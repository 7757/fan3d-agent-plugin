# Product grounding and brief

Read this reference before planning, writing, executing, or reviewing a
product introduction. The product can be any user-owned product. Fan3D is the
default visual engine, but the product evidence—not the available visual
effects—determines what the introduction may claim.

## Ground every claim

Start from the current workspace and the materials the user supplied for this
task, unless the user explicitly identified another product or evidence
source. In that case, use the supplied source and do not substitute the
workspace product. Treat each meaningful statement as one of:

- **Observed:** directly supported by inspectable product UI, project state,
  documentation, or media.
- **User-provided:** explicitly asserted or approved by the user but not
  independently verified in the workspace.
- **Inferred:** a cautious interpretation of evidence. Keep it qualified and
  never turn it into a factual superlative.
- **Proposed:** creative positioning or draft copy awaiting approval.
- **Unverified:** unsupported; omit it or ask for evidence.

Preserve exact product names, UI labels, numbers, compatibility statements,
and user-approved terminology. Do not infer behavior from a filename, visual
mockup, template title, or marketing tone. Never invent features, workflows,
customers, results, awards, performance figures, privacy or security claims,
pricing, availability, or comparisons. Use external research only when the
task calls for it, and do not send private workspace or user media to an
external service.

For consequential claims, keep a compact claim ledger:

| Claim | Status | Evidence | Allowed wording |
| --- | --- | --- | --- |
| What the audience should believe | Observed, user-provided, inferred, proposed, or unverified | Current supporting fact | Exact, qualified, approval-needed, or omit |

If evidence is incomplete, prefer accurate, lower-risk language over a more
impressive unsupported claim. For the creative brief, ask one concise question
only when the missing answer would materially change the promise, proof,
audience, or call to action. This does not replace project disambiguation,
authorization, explicit-file confirmation, bounded choices, or other safety
questions required by `fan3d-animation`.

## Build the brief

Synthesize the minimum useful brief instead of interviewing the user for every
field:

- **Objective:** what the introduction should make the audience understand,
  feel, or do.
- **Audience and context:** who sees it, what they already know, and where it
  will appear.
- **Primary promise:** one audience-relevant benefit the piece can support.
- **Proof:** one to three observable product facts that make the promise
  credible.
- **Call to action:** the next step, if the user wants one.
- **Format:** channel, aspect ratio, approximate duration, silent-viewing
  needs, and looping behavior.
- **Voice and visual character:** user-provided brand rules plus a small number
  of intentional adjectives.
- **Inputs:** existing project evidence, catalog-selectable resources, explicit
  user files still needed, and approved copy.
- **Constraints:** claims, authorization, accessibility, timing, output, and
  current capability limits.
- **Success criterion:** one observable test for whether the introduction
  communicates its promise.

Do not silently replace an explicit user objective, product position, script,
or brand direction. When offering a stronger alternative, preserve the
original as an option and explain the tradeoff briefly.

## Turn features into positioning

Use this causal chain:

```text
audience situation -> product behavior -> practical benefit -> supported proof
```

Lead with the benefit only when the proof can appear in the introduction. A
feature list is not a story, and emotional language is not proof. Prefer one
clear position over several generic virtues such as fast, simple, powerful,
and beautiful.

## Write screen-readable copy

Give each line one job:

- **Hook:** name the value or create a truthful question.
- **Proof line:** explain the visible feature or outcome without repeating the
  same information already obvious on screen.
- **CTA or close:** resolve the promise or state the next step.

Keep copy proportional to its readable dwell time. Favor concrete nouns and
verbs, remove filler, and preserve necessary product terminology. The video
must still communicate its core message without audio. Do not add narration,
testimonials, statistics, or legal qualifiers unless the user supplied or
approved them and the current workflow can present them legibly.

## Keep the plan executable

Before committing to a concept, classify every needed element as:

- already present and inspectable in the workspace;
- selectable from a live Fan3D catalog;
- an explicit local file the user must provide;
- a user or account authorization step;
- supported only if the current connection publishes the required capability;
- advisory or unavailable in the current workflow.

Discover live catalogs and capabilities when executing. Do not copy catalog
counts, stable IDs, tool schemas, or installed choices into this reference.
If the user delegates a creative choice, choose from current evidence and live
candidates and continue. Never disguise an unavailable effect with a different
operation that changes the intended meaning.

## Grounded brief output

A completed planning pass should make these facts easy to verify:

1. the primary audience, promise, proof, and CTA;
2. which claims are observed, user-provided, inferred, or still unverified;
3. the proposed format and success criterion;
4. the assets and capabilities already available;
5. the exact user input, authorization, or approval still required;
6. any assumption that materially shaped the concept.
